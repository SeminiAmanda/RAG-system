## q05
**Question:** How do updated weights reach the vLLM server during asynchronous GRPO training?

**Answer:**
> During asynchronous GRPO training the trainer pushes the new policy to the vLLM server after every `weight_sync_steps` training steps. The transfer is performed through the NCCL‑based weight‑transfer channel that the server exposes via the `--weight-transfer-config` option. If LoRA is used, the trainer writes the adapter to disk and posts it to the server’s runtime‑LORA endpoint (`VLLM_ALLOW_RUNTIME_LORA_UPDATING=1`), otherwise it merges the adapter into the base model and sends the full merged weights. In either case the updated weights are sent over the NCCL channel so that subsequent generations use the latest policy [2][3].

**Passages cited**:
### [2] trl/async_grpo_trainer.md | Asynchronous GRPO > How it differs from [`GRPOTrainer`]
```text
Tools and environment methods can be synchronous or asynchronous. Synchronous tools run on a thread pool sized to `max_inflight_tasks`, so a slow tool never blocks the other in-flight vLLM requests. Within one assistant turn, tool calls run in the order the model emitted them. Up to `max_inflight_tasks` synchronous tools therefore run at once, so a tool that reads or writes shared state must be thread-safe.

After every `weight_sync_steps` training steps, the updated weights are transferred to the vLLM server via NCCL so that subsequent generations reflect the latest policy.

Because generation and training run concurrently, the training samples may have been generated by a slightly older version of the model. The `max_staleness` parameter controls how many weight updates a sample can lag behind before being discarded.
```
### [3] trl/async_grpo_trainer.md | Asynchronous GRPO > LoRA
```text
`VLLM_ALLOW_RUNTIME_LORA_UPDATING=1` exposes the endpoint the trainer posts each new adapter to. Keep `--weight-transfer-config` even with `--enable-lora`: the trainer only chooses a sync mode when it starts, by which point the server is already up, and merged sync is the fallback.

`--max-lora-rank` must be one of `1, 8, 16, 32, 64, 128, 256, 320, 512`. It sets the highest rank the server can serve rather than the rank it will serve, so an `r=4` adapter works fine under `8`. `--max-loras` must be at least `max_staleness + 2`: the trainer keeps `max_staleness + 1` adapter versions registered so a rollout that started under an older policy can finish under it instead of switching policies mid-generation, and each sync loads the next version before it unloads the oldest. The trainer checks both values when it starts and tells you what to restart the server with.

vLLM loads adapters from disk rather than over the network, so the trainer writes each version under `<output_dir>/.vllm_lora/` and gives the server the path. If the server runs on a different machine, that directory has to be on a filesystem both of them can see.
```

**Question:** What is colocate mode for vLLM generation in GRPOTrainer, and what is its trade-off?

**Answer:**
> Colocate mode means that vLLM runs **inside the same process as the GRPOTrainer** and shares the GPU memory with the training model. This eliminates the need to launch a separate vLLM server and can improve GPU utilisation. The trade‑off is that the two workloads compete for the same GPU memory, which can lead to memory contention on the training GPUs. [1][5]

## q35
**Question:** How does GRPOTrainer run several async reward functions, and when is that useful?

**Answer:**
> GRPOTrainer runs several async reward functions by awaiting them concurrently (using `asyncio.gather`) so that their latency overlaps. This allows you to pass a list of reward functions that can be either synchronous or asynchronous, and the trainer will compute the reward as the sum (or weighted sum) of the individual rewards. Async reward functions are useful when the reward depends on slow I/O operations, such as calling a remote service or performing a database lookup, because running them concurrently reduces overall wait time. [1][3]

**Passages cited**:
### [1] trl/grpo_trainer.md | GRPO Trainer > Customization > Using a custom reward function > Example 5: Asynchronous reward functions
```text
Custom reward functions can also be defined as `async def` coroutines. This is useful if your reward depends on slow I/O (for example, calling a remote service). When you pass multiple async reward functions, [`GRPOTrainer`] executes them concurrently so their latency overlaps.

Below is a minimal example of an async reward function that simulates an I/O-bound operation:

```python
import asyncio

async def async_reward_func(prompts, completions, **kwargs):
    # Simulate an I/O-bound call (e.g., HTTP request, database lookup)
    await asyncio.sleep(0.01)
    # Simple toy reward: 1.0 if the completion is non-empty, else 0.0
    return [1.0 if completion else 0.0 for completion in completions]
```
```
### [3] trl/grpo_trainer.md | GRPO Trainer > Customization > Using a custom reward function
```text
The [`GRPOTrainer`] supports using custom reward functions instead of dense reward models. To ensure compatibility, your reward function must satisfy the following requirements:

Reward functions can be either synchronous Python callables or asynchronous `async def` coroutines. When you provide multiple asynchronous reward functions, they are awaited concurrently (run in parallel via `asyncio.gather`) so their latency overlaps.

> For example, use `DynamoExporter` for a PyTorch‑based runtime, `OnnxExporter` for any ONNX runtime, `ExecutorchExporter` for ExecuTorch, or `OpenVINOExporter` for OpenVINO. Swap the exporter you instantiate to switch runtimes.  
> [1][5]

**Passages cited**:
### [1] transformers/exporters.md | Exporters > Export a model
```text
All exporters share the same interface. Create an exporter with a config, and call [`~exporters.HfExporter.export`].

Switch between runtimes by swapping the exporter class.

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
from transformers.exporters import DynamoExporter, DynamoConfig

model = AutoModelForCausalLM.from_pretrained("Qwen/Qwen3-0.6B")
tokenizer = AutoTokenizer.from_pretrained("Qwen/Qwen3-0.6B")

>

>    /your/path/to/slime/tools/convert_hf_to_torch_dist.py \
>     ${MODEL_ARGS[@]} \
>     --hf-checkpoint /your/path/to/huggingface/models/GLM4.5-355B-A32B \

> 
> 1. In `/your/path/to/megatron/models/GLM4.5-355B-A32B_torch_dist`, change `latest_checkpointed_iteration.txt` from `release` to `0` and rename the `release` folder to `iter_0000000`.  
> 2. In the config, set `megatron_lm_no_load_optim` to `true` so no optimizer states are required.

**Answer:**

> You can cut that down by:
> 
> * Loading the model in a lower‑precision dtype, e.g. `torch_dtype="auto"` which will use `bfloat16` for models trained with it [1].
> * Quantizing the model to 8‑bit or 4‑bit using BitsAndBytes, e.g. via a `BitsAndBytesConfig` passed to the pipeline [1].

**Passages cited**:
### [1] transformers/conversations.md | Chat basics > Performance and memory usage
```text

> [!TIP]
> Refer to the [Quantization](./quantization/overview) docs for more information about the different quantization backends available.
